Chapter 1

Introduction and concepts

1.1 · What AMS is

AMS — Advanced Messaging System is the tool with which the administrators of a Linux machine send text messages to users and know who has confirmed reading them. It answers a question that the system's own tools leave open: “who has not read it yet?”

wall and write write to the terminals of logged-in users without keeping track of anything; notify-send shows a notification that may disappear; the motd and login banners are fixed texts. None of them keeps a state per message and per user. AMS puts the pieces together (logind, the terminals, desktop autostart, zenity, the journal) and adds exactly this state.

Version 0.2.0 is written in C (the 0.1.0 prototype was in bash): two programs, no daemon, no database. The ams command always runs as root and writes to the message store; on the user's side the helper ams-user reads the mailbox and records the confirmation, in two ways: in the shell prompt (ams-user prompt) and in the graphical session (ams-user agent).

i
Note. this manual describes how AMS works. The contract that every version must honour (states, invariants, interruptions, message store format) is chapter 20, “Specification”; the user manual explains how to use AMS, without technical jargon.

1.2 · Basic concepts

A few concepts are enough to read the rest of the manual. They are the same in the code, in the tests and in the manuals.

Message
a text (at most 65536 bytes) with an optional title and an optional expiry, identified by a sequential number, the ID. The sender is the administrator who ran ams.
Recipient
a human user of the machine to whom the message is addressed: by name, by group (@gruppo), everyone (all) or the logged-in users (online).
Reference copy
the message in /var/lib/ams/sent/ID/, readable only by root: what was sent, to whom, when, with which expiry. It is the authoritative source.
Mailbox
a user's /var/lib/ams/users/U/ folder: a working copy that the user controls, with the subfolders inbox, read, acks and state.
Channel
where the user sees the message and confirms it: a terminal (terminale pts/N, terminale tty3) or the desktop (desktop).
Confirmation
the user's statement of having read the message, written into their mailbox in acks/ID with date and channel. The first one counts.
Postponement
the answer “no” in the terminal or «Più tardi» (“Later”) on the desktop: the question comes back after AMS_REMIND_MINUTES minutes, or at the next login.
State
for each recipient exactly one of three: sent, delivered, confirmed. Revoked and expired are properties of the message, not states.

The code lives in src/ and is organised in small modules with clear-cut responsibilities. This is the map that the manual explores chapter by chapter.

Chapter 2

General architecture

2.1 · Architectural principles

AMS is small on purpose: two programs, files in a single folder, the systemd libraries already present on the system. The design favours verifiability: every state can be reconstructed by looking at the files, and every step that can be interrupted leaves a mark that the next command knows how to repair.

2.2 · The three privilege domains

A message crosses three domains with different privileges. The rule is simple: everything that passes between root and a user crosses a controlled boundary, in both directions.

i
Note. the TUI is not a separate domain: it is ams itself, and its actions are the commands run in a child process (chapter 14.1).

2.3 · The two programs

The Makefile produces two executables and one catalog per language. The common parts (comune testo lingua evento utente sessioni) go into both; ams adds ams.o, guida.o, archivio.o and tui.o.

Both depend only on glibc and libsystemd (sd-login for sessions, sd-journal for the log). At run time they also need sudo, zenity, systemd-run and date; notify-send if available.

2.4 · The path of a message

The complete path touches every subsystem. Here it is in brief; each step has its own chapter.

2.5 · Sessions and channels

AMS does not use utmp, which does not record many modern terminals, but logind and the terminal devices. The useful question is not “how is the user logged in” but “on which channels can I reach them right now”.

  • The mailbox acts as a queue: a message that reaches no channel when it is sent appears at the next login (question in the terminal) or at the agent's first round (dialog).
  • Writing the text to a terminal does not count as a confirmation: the question arrives at the next prompt.
i
Note. a terminal in which the user switched identity with su still belongs to whoever opened it: ams send does not write to it. The shell hook reaches the user anyway at the next prompt.
Chapter 3

Repository, build and installation

3.1 · File map

The repository contains the C code, the language catalogs, the files to install on the system, the manuals with their sources, the tests and the consistency checks. The following table is the file map: the lines are counted every time the manual is generated, and tools/check-docs.py fails if a code file is missing or if one that does not exist is listed.

The chapters of the manuals are in docs/sorgenti/utente/ and docs/sorgenti/tecnico/, one file per chapter; docs/decisioni-e-storia.md and CLAUDE.md collect the decisions and the working agreements, docs/revisione-avversariale.md the two external reviews. The bash prototype (version 0.1.0) is in the repository history.

3.2 · Building: the Makefile

The build is a Makefile with no external tools besides gcc, pkg-config (for libsystemd) and gettext. Everything ends up in build/ (or in a folder chosen with B=); the installation folders are compiled into the program with -DLIBDIR and -DLOCALEDIR.

Makefile (excerpt)
AVVISI = -Wall -Wextra -Wpedantic -Wformat=2 -Wformat-security -Wshadow -Wpointer-arith \
         -Wcast-qual -Wwrite-strings -Wstrict-prototypes -Wmissing-prototypes -Wvla \
         -Wnull-dereference -Wimplicit-fallthrough -Wundef -Werror
DIFESE = -D_FORTIFY_SOURCE=3 -fstack-protector-strong -fstack-clash-protection -fcf-protection -fPIE
LDFLAGS += -pie -Wl,-z,relro,-z,now -Wl,-z,noexecstack

Warnings are errors (-Werror): the code does not build if gcc finds anything to object to. The meaning of each hardening flag is in chapter 17.3.

3.3 · install.sh step by step

  1. It relaunches itself with sudo if it is not root, and picks the administrators' group: the first one that exists among sudo, wheel, admin (otherwise root). It warns if zenity, loginctl or systemd-run are missing.
  2. If the programs are missing from build/, or were built for other folders (the LIBDIR path does not appear inside build/ams), it builds them with make PREFIX=… (gcc, make, pkg-config, libsystemd-dev and gettext are needed).
  3. It installs $PREFIX/lib/ams/ams-user (755), the catalogs in $PREFIX/share/locale/LINGUA/LC_MESSAGES/ams.mo and $PREFIX/bin/ams with owner root:gruppo and permissions 750; it removes the files of the bash prototype and an old sbin/ams. PREFIX is /usr/local.
  4. It installs the manuals in $PREFIX/share/doc/ams/, the configuration (only if missing), the shell hooks and the autostart entry, replacing @LIBDIR@ and @VARDIR@.
  5. It adds to /etc/bash.bashrc the line marked # AMS hook (on Debian, interactive non-login shells do not read /etc/profile.d); if the system zshrc exists, it adds the line that sources ams.zsh; for fish it writes /etc/fish/conf.d/ams.fish.
  6. It creates /var/lib/ams and users/ (755) and sent/ (700).
  7. It closes the agents of the previous version (the bash ones too): they restart, updated, at the first send or at login.

3.4 · What it installs, and where

i
Note. users have no command: ams-user is not in the PATH and, when run by hand without prompt or agent, replies that it is an internal helper and exits with 1.

3.5 · Before committing a change

  1. make (all warnings are errors) and make prove.
  2. make pot if texts to translate have changed, then the translation in po/it.po.
  3. python3 docs/sorgenti/build.py, then tools/check-docs.py: generated manuals up to date, reference aligned with the help, catalogs complete, file map complete, internal links valid, tests run on the current code (chapter 21.5).
  4. tests/engine.sh always; tests/help-tui.py if the help has changed; tests/tui.py and tools/schermate-tui.sh if the TUI has changed; make sanitizer with AMS_BUILD=build-san tests/engine.sh, make analizza and tests/fuzz/esegui.sh if the code that reads data has changed; tests/container/esegui.sh if sending, delivery, confirmations or permissions have changed; tests/vm/esegui.sh if the desktop has changed.
  5. A test of the affected flow in test mode (chapter 4.4); for the desktop, sudo and other users, a live test after ./install.sh, done by whoever has the root password.
!
Warning. test results are committed together with the change: each suite writes its result with the commit and the code fingerprint, and chapter 21 shows them next to the current fingerprint.
Chapter 4

Startup and configuration

4.1 · Starting ams

The main of src/ams.c is short and its order is a rule: nothing runs without root, not even the help. Before looking at the arguments it reads the environment and the language; then, if it is not root and not in test mode, it relaunches itself with sudo.

src/ams.c (in brief)
int main(int argc, char **argv)
{
	const char *cmd = argc > 1 ? argv[1] : "";

	ams_init("ams");
	lingua_init();
	if (geteuid() != 0 && !ams_test)       /* anche per la guida e la versione */
		rilancia_con_sudo(argv);           /* execvp("sudo", "--", /proc/self/exe, …) */
	umask(022);
	if (!*cmd && isatty(0) && isatty(1)) { /* ams da solo in un terminale */
		recupera();
		if (ams_tui())
			return 0;                      /* terminale troppo piccolo: la guida */
	}
	if (!*cmd || !strcmp(cmd, "help") || !strcmp(cmd, "-h") || !strcmp(cmd, "--help"))
		{ ams_guida(); return 0; }
	if (!strcmp(cmd, "version") || !strcmp(cmd, "--version")) { … }
	/* comando sconosciuto: die(); purge escluso, prima di ogni comando: recupera() */
	…
}
  • rilancia_con_sudo reads its own path from /proc/self/exe and calls execvp("sudo", ["sudo", "--", percorso, argomenti…]): the arguments arrive unchanged, and -- prevents them from being taken as sudo options.
  • Under sudo the environment is what sudo preserves: usually LANG and the language variables are kept, AMS_TEST is not. SUDO_USER tells who launched the command: it becomes the sender (from) and the author of the events.
  • Recovery of interrupted sends (chapter 8.6) runs before send, list, status, revoke, remind, log and the TUI; not before purge, which skips incomplete sends by itself.
  • An unknown command ends with die: ams: comando sconosciuto: X (ams --help per la guida) (in English: “unknown command: X (ams --help for the guide)”), exit status 1.

4.2 · Starting ams-user

ams-user never relaunches itself: it runs with the identity of whoever launches it, that is the user. Its main has a different order, dictated by the desktop agent.

4.3 · The environment and test mode

ams_init in src/comune.c sets the working folders. The defaults are compiled into the program; the environment variables count only in test mode: a root program does not take folders from the environment of whoever launches it.

AMS_TEST=1
ams does not relaunch itself with sudo, does not wake or start agents, does not change identity in child processes and writes only to the “terminal” AMS_TEST_TTY. An ordinary user who sets it keeps their own permissions (scenario G4: «Permesso negato», “Permission denied”, as soon as ams is executed), and sudo removes it from the environment.
AMS_TEST_TTY=file
the “terminal” that ams send writes to in test mode; empty: none.
AMS_BUILD=cartella
for the tests: the programs to test (for example build-san).

4.4 · Testing without root

The code is tested from the repository folder as an ordinary user, on a test message store, after make. This is how tests/engine.sh, tests/tui.py and tests/help-tui.py run.

A test without root
nicfio@server:~/AMS$ make
nicfio@server:~/AMS$ export AMS_TEST=1 AMS_LIB=$PWD/build AMS_LOCALEDIR=$PWD/build/locale
nicfio@server:~/AMS$ export AMS_VAR=/tmp/prova AMS_CONF=/dev/null AMS_TEST_TTY=/tmp/tty
nicfio@server:~/AMS$ build/ams send --to nicfio "Prova"
Messaggio 1 inviato a 1 utente.
nicfio@server:~/AMS$ script -qec 'build/ams-user prompt' /dev/null
!
Warning. without AMS_TEST, build/ams goes through sudo; if the sudo credentials are still valid it starts as root without asking anything, on the real message store. In tests always set test mode.
i
Note. in test mode the recipients are real users of the machine (getpwnam), but their mailboxes are folders of the test message store written with the identity of whoever runs the test: tests/engine.sh uses root as its second recipient.

4.5 · The configuration: ams.conf

The configuration is a data file, not a script: in the bash prototype it was read with source, by root and by the users, and could execute code. Now conf_leggi in src/testo.c reads at most 65536 bytes of it and conf_da_testo accepts only two keys, with positive integers.

etc/ams/ams.conf
# Dopo quanti minuti riproporre un messaggio rimandato dall'utente
AMS_REMIND_MINUTES=30

# Ogni quanti secondi l'agente del desktop ricontrolla i messaggi
# (i nuovi messaggi lo svegliano comunque subito)
AMS_AGENT_POLL=60
  • Each line loses its comment (from # onwards) and all spaces; a line that is still longer than 255 characters is not valid.
  • The value must consist of digits only, at most 6, and be greater than zero: 0, -3, abc and $(…) are ignored and the default stays (tests/engine.sh, group 5).
  • Unknown keys are ignored; a missing file, or one that is not a regular file, counts as empty.
  • ams itself does not read the configuration: the two keys concern only what ams-user does.
Chapter 5

The message store

5.1 · Structure

The message store is made of files and folders under /var/lib/ams. One part belongs to root, one part to each user: the boundary between the two is the heart of AMS security. There is no database and no index: every piece of information is in a file that can be read with cat.

i
Note. the files incomplete, ritiro and failed are internal recovery markers: they say that an operation must be completed or has been cancelled. They are not states of a message or of a recipient, and no command shows them as such (chapter 20.2).

5.2 · Format of a message

A message is a UTF-8 text file: a chiave: valore (key: value) header, an empty line, the text. The same file, byte for byte, is the reference copy in sent/ID/msg and the copy in the mailbox of each recipient.

sent/12/msg
format: 1
id: 12
from: admin
date: 1790714288
title: Manutenzione
expires: 1790800688

Sabato dalle 8 alle 12 il server sarà spento.

5.3 · Message numbers

Every message has a sequential number. prossimo_id in src/ams.c takes it under an exclusive flock on sent/.seq.lock: two simultaneous ams send runs never get the same number.

  • It reads the last number from sent/.seq (0 if missing or not a number), increments it and creates the folder with mkdir(…, 0700).
  • If the folder already exists, it moves on to the next number: this happens if .seq went backwards, for example after a power failure that lost the last write. No message is ever overwritten.
  • It writes the new value with scrivi_atomico and releases the lock by closing the descriptor.
  • A number taken and never used (an interruption right afterwards) remains a gap in the numbering: harmless.

5.4 · Owners and permissions

A user can delete or modify the files in their own mailbox: they only spoil their own copy. The reference copy stays in sent/, and a message deleted from the mailbox simply shows up as not confirmed. A confirmation written by hand remains a statement by the user (chapter 20.1).

!
Warning. the effective permissions of the files created by U also depend on the process umask: the child of come_utente sets it to 022, ams-user uses the one of the user's session. The real protection is the users/U folder at 700.

5.5 · Reading and writing files safely

All file I/O goes through a few functions in src/comune.c with fixed rules. These are the functions that make it safe to read what users write and that guarantee durability after an interruption.

Every descriptor is opened with O_CLOEXEC: no open file is passed on to the programs launched by AMS (zenity, sudo, systemd-run, the editor). Memory is requested with xmalloc and texts grow in a buf_t (chapter 24.5): no fixed-length buffer receives data that comes from outside.

5.6 · Preserving the message store

AMS has no backup or restore command: the message store is made of files, and the only tools provided are the purge of old messages (ams purge, chapter 9.3) and complete removal (install.sh --purge).

  • A reset message store reuses message numbers, the journal does not: this is why ams log ID reads only the events after the message's sending date (chapter 18.4).
  • A copy taken while a send is in progress contains the incomplete marker: given how recovery works (chapter 8.6), after a restore that send would be completed by the first ams command.
!
Warning. backing up and restoring the message store have not been tested: whoever does it must preserve owners and permissions (in particular U's users/U with 700 and root's sent/ with 700).
Chapter 6

Recipients and sessions

6.1 · From --to to the list

risolvi_destinatari in src/ams.c turns the value of --to into the list of recipients. It does so before taking a number and before writing anything: an error here leaves no trace in the message store.

  • The value is split on commas; each part is one of the four forms in the figure. Empty parts (two commas in a row) are skipped; a space, on the other hand, becomes part of the name, which therefore does not exist: this is why the help asks for names separated by commas without spaces.
  • An unknown user or group ends with die («utente inesistente: pippo», «gruppo inesistente: x»); for the user this is scenario B6 on the test machine.
  • Duplicates are removed along the way (scenario B2) and the final list is in alphabetical order: this is the order of the deliveries and of sent/ID/recipients.
  • An empty list (for example a group with no members) ends with «nessun destinatario» (scenario B7).
  • An explicit name may also be a system account or root: the filter on human users applies only to all and online.

6.2 · Human users, logged-in users, groups

Everything goes through the system interfaces (getpwent, getgrnam, libsystemd's sd-login library): LDAP users or users from other name services work if the system exposes them this way. all excludes root and system accounts because they have a UID below UID_MIN or a non-login shell (scenario B4).

i
Note. online counts the sessions of class user and then filters them against the human users: the test VM showed that root and logged-in system accounts (for example the graphical login manager) ended up among the recipients (scenario B5). They are now excluded even when logged in.

6.3 · A user's terminals

terminali_utente collects the terminals to which ams send writes the text when sending. There are two sources, because neither is enough on its own.

  • Here the owner of /dev/pts/N serves only to find the candidates: at the moment of writing, scrivi_terminale reopens the terminal and checks the owner of the opened terminal (chapter 8.4). The name /dev/pts/N does not identify a session: between the search and the write it might pass to another user.
  • In test mode there is a single «terminal»: the file AMS_TEST_TTY, if set.
  • An ssh session without a terminal (scp, remote commands) and services have no terminals: they are not touched (scenario C3).

6.4 · The graphical session

sessione_grafica tells whether a user has an X11 or Wayland session open. It is needed in two places, with the same code.

A user with several graphical sessions (for example a local desktop and a remote one that creates a new session) still has a single agent: the lock ams-agent.lock lives in $XDG_RUNTIME_DIR, which is unique per user (chapter 12.1). The behaviour with several simultaneous desktops of the same user has not been tested.

Chapter 7

Root with the user's identity

7.1 · The danger of symbolic links

The mailbox users/U belongs to the user, who can replace its subfolders with symbolic links, pipes or odd files. If root wrote into it directly, it would follow the link and could write anywhere; if it read from it, it could show files the user is not allowed to read. This is why every access by root to the contents of a mailbox happens in a child process with the user's identity: come_utente in src/utente.c, in place of the runuser used by the prototype.

In the child the user's permissions apply: a link to /etc leads to «permission denied», and the worst the user can achieve is to spoil their own copy. Scenario G1 on the test machine checks this: with the mailbox turned into a link to /etc, ams send writes nothing in /etc and the recipient stays «sent, not delivered».

i
Note. only the folder users/U itself is touched by root: root creates it (700) inside users/, which belongs to root, and hands it over to U with lchown. If it already exists it must be a real folder (lstat); if it is still owned by root, because a send was interrupted between creation and handover, it is handed over at the next send (scenario F6).

7.2 · How the child process starts

come_utente(u, fn, arg, in, out, max, secondi) runs fn(arg) in a child process with the identity of u. The parent passes it data on stdin, collects its output on a pipe and waits for it to finish, always with a time limit.

src/utente.c (abridged)
static void figlio(const utente_t *u, come_utente_fn fn, void *arg, int in, int out)
{
	/* stdin e stdout sulle pipe, stderr su /dev/null */
	if (geteuid() == 0 && !ams_test) {
		/* identità completa dell'utente: gruppi, poi gruppo, poi utente */
		if (initgroups(u->nome, u->gid) < 0 || setresgid(u->gid, u->gid, u->gid) < 0 ||
		    setresuid(u->uid, u->uid, u->uid) < 0)
			_exit(126);
		if (getuid() != u->uid || geteuid() != u->uid || getegid() != u->gid || setuid(0) == 0)
			_exit(126);                       /* se torna root, qualcosa non va */
	}
	if (chdir("/") < 0)
		_exit(126);
	umask(022);
	_exit(fn(arg) & 0xff);
}
  • The order matters: first the supplementary groups (initgroups), then the group, then the user; after setresuid the group can no longer be changed.
  • The child checks that it can not become root again: if setuid(0) succeeded, the identity would not really have been assumed. Any anomaly ends with exit code 126, which the parent turns into an error.
  • After the identity change the kernel makes the process non-inspectable by the user (not «dumpable»): U cannot read its memory while it works.
  • In test mode, without root, the child keeps the identity of whoever runs the test.

7.3 · Time limits and results

The child runs with the user's identity, so the user can stop it (SIGSTOP) or slow it down. ams must not hang: the time limit applies both while the child is writing and afterwards, until it exits.

The pipes are created with O_CLOEXEC; the child's stdin is written in non-blocking mode, alternating with reading the output via poll (at most one second per round), so a child that does not read does not block the parent. gcc's static analysis found pipes left open in an error path of come_utente: fixed (chapter 21.7).

7.4 · Operations on the mailboxes

All operations on the mailboxes are functions in src/archivio.c that run inside the child. They are small on purpose: each does one thing, with paths built from the message number.

i
Note. revocation and deletion do not ask the user whether the folder exists: if users/U is not there (a user never reached) there is nothing to remove and the operation succeeds without starting the child.
Chapter 8

Sending and recovery

8.1 · Options and text

cmd_send in src/ams.c checks everything it can check before writing to the message store: options, text, expiry, recipients. An error at this stage ends with die and leaves nothing behind.

  • Options end at the first argument that is not an option: from there on the arguments, joined by a space, are the text. Without text and without --file the text is read from stdin (at most 64 MiB).
  • An unknown option («opzione sconosciuta: --level») or one without a value («manca il valore di --to») ends at once. --level belonged to version 0.1.0 and is rejected (tests/engine.sh, group 3).
  • A duration is a number followed by m, h or d; everything else is interpreted by date -d … +%s in a child process (for example "2026-10-04 12:00"). Dates in words are those understood by date, in English.
  • Trailing newlines are removed from the text, which is then cleaned (chapter 8.7). A text made only of spaces is «messaggio vuoto»; beyond 65536 bytes, after cleaning, it is «messaggio troppo lungo»: the desktop dialog receives the text as an argument to zenity, and Linux does not accept an argument larger than 128 KiB.

8.2 · The sending sequence

After the checks, sending is a fixed sequence. The order is chosen so that every interruption leaves a state that the next command can recognise and repair.

A successful send
admin@server:~$ sudo ams send --to @sviluppo --title Manutenzione --expires 2d "Sabato dalle 8 alle 12 il server sarà spento."
Messaggio 12 inviato a 2 utenti.

8.3 · Verified delivery

«Delivered» means that the copy was in the mailbox, verified, at the time of delivery. consegna_copia in src/archivio.c writes and checks in the same child process; only if it succeeds does ams send record the line in delivery.

  • Root prepares only users/U (chapter 7.1); the subfolders and the copy are written by the child with U's identity.
  • If the message is already in read/ or acks/ the copy is not rewritten: recovery does not present again to a user a message already read or confirmed (tests/engine.sh, group 2).
  • The copy is born as inbox/ID.tmp and becomes inbox/ID through a rename: ams-user, which lists only names made of digits, never sees a half-written file.
  • A failure for one recipient (mailbox not writable, link to /etc, timeout) does not stop the others: the event NON_CONSEGNATO goes to the log and sending continues (scenario F1).

8.4 · Writing to the terminals

For each terminal from terminali_utente (chapter 6.3), ams send writes the formatted text in the language of whoever uses that terminal. Writing to the terminal does not count as confirmation: the question comes at the next prompt.

The text written to the terminal of an Italian-speaking user

8.5 · Waking or starting the agent

After the copy, sveglia_agente makes the dialog appear on the desktop at once, without waiting for the agent's periodic check. If the user has no graphical session (or in test mode) it does nothing.

  • The signal goes only to a ready agent: the PID written in /run/user/UID/ams-agent.pronto (at most 64 bytes, without following links), which the agent writes after it has prepared to receive the signal (chapter 12.2).
  • The signal is sent from a child with U's identity, and only if /proc/PID/cmdline is exactly LIBDIR/ams-user followed by agent: it cannot reach other users' processes, nor a process of U that had inherited an old PID.
  • If there is no ready agent, systemd-run --user --machine=U@.host --collect --quiet starts one in the systemd user manager, which already knows the graphical environment of the session. If an agent was starting, the new one finds the lock and exits; the one that was starting reads the mailbox anyway on its first round (scenario I8: dialog in about half a second).
i
Note. the agent writes ams-agent.pronto in $XDG_RUNTIME_DIR, while ams send looks for it in /run/user/UID: they coincide in sessions started by logind, which is the supported case.

8.6 · Recovery

recupera runs at the start of almost every command (chapter 4.1) and repairs what an interrupted command left half done: sends, revocations, deletions. It is idempotent: repeating it changes nothing.

  • The lock tells a send in progress from an interrupted one: ams send holds it for the whole delivery and the kernel releases it when the process dies, even with SIGKILL. Without this rule recovery, started during a long send, delivered in parallel and recorded duplicates (found by the real-world suite; scenarios F3 and F5).
  • Copies already recorded are checked again because, after a power failure, a delivery line might be on disk while the copy is not (tests/engine.sh, group 9).
  • In the last recorded run on the test machine (scenario F3), an ams send killed with SIGKILL after 4 deliveries out of 68 was completed by the next command in less than a second.
!
Warning. recovering a send in which some copy still cannot be written leaves incomplete and warns: «messaggio N ancora non consegnato a K destinatari (vedi ams status N)». Every following command retries.

8.7 · Cleaning the text

A message's text and title come from an administrator but end up in the users' terminals: they must not be able to move the cursor, change the window title or write to the clipboard. pulisci in src/testo.c removes, in three passes, everything a terminal could interpret as a command.

  • An OSC sequence without a final BEL is not removed as a sequence: its ESC disappears in pass 2 and the rest remains as harmless text (tests/prove-unita.c).
  • Normal UTF-8 text stays intact, including non-breaking spaces (C2 A0).
  • pulisci is applied to text and title before they are saved, to what ams reads from the mailboxes (chapter 10.2), to the lines of ams log and to what the TUI shows of the commands it ran.
  • It gives the same result as the bash prototype (sed and tr): the two were compared on 2000 random texts full of sequences and control characters before the prototype was removed. Scenario G2 checks that no ESC reaches the terminal.
Chapter 9

Revocation, reminders and deletion

9.1 · Revoking: ams revoke

ams revoke ID revokes a message: whoever has not seen it yet will not see it, open questions and dialogs close by themselves. The revocation takes place at the instant sent/ID/revoked appears: from then on no new delivery, and no confirmation with a later date counts.

  • Serialising revocation with sending comes from the second review: before, a copy could arrive after the revocation. tests/engine.sh (group 9) checks that ams revoke waits for a lock held for 2 seconds; scenario F7 revokes a send to many users while it is in progress, and no copy is left behind.
  • If the revocation arrives during the send, ams send ends with «Messaggio N ritirato durante l'invio: consegna interrotta.»: the recipients not yet reached stay «sent».
  • The question in the terminal and the dialog check inbox/ID every second and close (scenarios E3 and I6); a confirmation that arrives between their last check and the revocation does not count, because its date is later than revoked (chapter 13.1).

9.2 · Reminding: ams remind

ams remind ID brings the question back at once to those who have not confirmed yet, even if they had postponed it. It rewrites nothing: it removes the postponements and wakes the agent.

  • A revoked or expired message cannot be reminded: «il messaggio N è stato ritirato: nessuno da sollecitare» (tests/engine.sh, group 10).
  • The recipients' state comes from destinatari, the same function used by ams status: the reminder goes to those who are delivered. Those who are sent do not have the copy (recovery will complete it), those who have confirmed must not be disturbed («sollecitati 0 destinatari»).
  • For each of them, as the user, state/ID.term and state/ID.gui are removed; then sveglia_agente. The question comes back at the next prompt (scenario D5); the dialog reappears at once (scenario I11: 0.37 s in the last recorded run).
  • The reminder takes no lock: if a confirmation arrives in the meantime, removing the postponements of someone who has confirmed has no effect (chapter 20.4).
A reminder
admin@server:~$ sudo ams remind 12
Messaggio 12: sollecitati 3 destinatari.
i
Note. before the reminder existed, the test VM found an edge case: an ams remind arriving within a second of «Più tardi» (“Later”) was lost, because the agent recorded the postponement on its next round. Now the agent records the answer as soon as zenity closes (chapter 12.3).

9.3 · Deleting: ams purge

ams purge DURATA deletes the messages sent more than DURATA ago, together with the copies, confirmations and postponements in the mailboxes. The events stay in the journal.

  • The rename is the point at which the message stops existing for all commands: elenca_numeri sees only names made of digits. ams list reads what it needs from each message before using it and skips a message that has disappeared in the meantime (riassumi returns false).
  • A deletion interrupted after the rename is completed by the recovery of the next command (tests/engine.sh, group 9).
  • ams purge does not run recovery before itself: it skips incomplete sends anyway.
A purge
admin@server:~$ sudo ams purge 90d
Cancellati 4 messaggi più vecchi di 90d.
!
Warning. after the deletion message numbers are not reused (the .seq sequence stays), but ams log of a deleted number no longer finds the message: its history can then be read only with journalctl AMS_MESSAGGIO=ID.
Chapter 10

State: list, status and the summary

10.1 · The state deduced from the files

A recipient's state is not written anywhere: stato_destinatario in src/ams.c deduces it every time from sent/ID/delivery, from the confirmation in the mailbox and from the reference copy. The expiry and revocation that count are root's, not those of the copy, which the user might have altered.

  • The date of the confirmation is the number before the space in acks/ID (0 if it is not a number); the rest of the line is the channel, translated only when it is shown (canale_testo).
  • A confirmation with the same date as the revocation counts; one from the second after does not (tests/engine.sh, group 9).
  • A recipient is in exactly one of the three states: the function returns a value of stato_e (INVIATO, CONSEGNATO, CONFERMATO) plus, separately, if the confirmation was late, its date and channel.

10.2 · Reading the mailboxes

ams status and ams list read the confirmations from the mailboxes, which the users control. leggi_casella in src/archivio.c treats them as untrusted data and reads them once per user, in a single child process.

  • The child receives on stdin the numbers of the messages that exist in sent/ and looks only for those: thousands of fake files in acks/ do not matter (5000 files: ams list under a second, tests/engine.sh group 9; before the fix, 3.9 s).
  • Of acks/ID it reads at most 200 bytes, and only if it is a regular file opened without blocking: a pipe in place of the confirmation does not block ams status (group 9).
  • Of state/ID.* it reads the most recent modification date: that is the time of the postponement.
  • The child's output (at most 4 MiB) goes through pulisci before it is interpreted: a confirmation forged with escape sequences does not reach the administrator's terminal (scenario G3).
  • The mailboxes read stay in memory for the whole command; the TUI forgets them at every refresh (caselle_svuota). Deliveries are read once per message (leggi_consegne).

10.3 · A message's summary

In the list of messages, in ams list and in the TUI, a message is summarised by its recipients: how many are in each of the three states, in words and with a bar, plus the properties revoked and expired. No other word describes the state of a message (chapter 20.3).

	long long id;

	int confermato, consegnato, inviato;  /* i destinatari nei tre stati */
	bool ritirato, scaduto;               /* proprietà del messaggio */
} riassunto_t;

The two query commands show the same state at two levels: the list of messages and the detail of one. Both run recovery first; after that, only reads, without locks.

Chapter 11

Receiving in the terminal

11.1 · The shell hooks

Each shell has its own hook, installed where that shell reads it. They all do the same thing: if the mailbox contains messages, they run ams-user prompt, right at login and then before every prompt.

The message text reaches the terminal at send time whatever the shell: root writes it, not the shell (chapter 8.4). dash, ksh and similar shells have no place to hook into before the prompt: the question arrives at the next login, or through the desktop dialog (scenarios K of the test machine). profile.d/ams.sh is written in plain sh because every shell reads it: it hands bash over to ams.bash, leaves zsh to its own hook and asks the others at login.

i
Note. zsh reads the system-wide zshrc: if it is installed after AMS, just run install.sh again to add the line. fish reads conf.d even if it arrives later.

11.2 · From the hook to the question

etc/ams.bash (excerpt)
__ams_prompt() {
	local s=$?
	# Controllo senza processi esterni: con la casella vuota non costa nulla.
	if compgen -G "$__AMS_INBOX/[0-9]*" >/dev/null; then
		@LIBDIR@/ams-user prompt
	fi
	return $s
}
  • The hook acts only in an interactive shell, if ams-user exists, and once per shell (variable __AMS_HOOK, in fish __ams_hook).
  • It adds __ams_prompt to PROMPT_COMMAND: as an element if it is an array (bash 5.1 and later), at the front if it is a string. It preserves $?: the user's prompt sees the result of their last command.
  • The mailbox check uses compgen -G, a bash builtin that starts no processes: with an empty mailbox the prompt costs nothing. zsh does the same with the (N) glob, fish with string match on the names (fish globs have no [0-9]).
  • In a login shell it calls ams-user prompt --login straight away: the message appears before the first prompt (scenario C1b: about 0.3 s after login).
  • On Debian, interactive non-login shells (the desktop terminals) do not read /etc/profile.d: the hook is also called from /etc/bash.bashrc (chapter 3.3).

11.3 · ams-user prompt

ams-user prompt in src/ams-user.c takes the messages in the mailbox in numeric order. If stdin is not a terminal it does nothing; the confirmation channel is the terminal name (terminale pts/3).

  • in_attesa lists inbox/ (only names made of digits, and regular files). A message whose confirmation is already present, because of an interruption between the confirmation and the move, goes to read/ without asking; an expired one goes to read/ without a confirmation.
  • A message postponed less than AMS_REMIND_MINUTES minutes ago (modification time of state/ID.term) is not asked about: it is counted, and at the end the one-line reminder appears. With --login the postponement does not apply.
The question at the prompt

Note. ams-user runs inside the user's prompt: it never ends with an error that would disrupt the shell, and any problem it meets (unreadable mailbox, no terminal) turns into doing nothing.

11.4 · The question and the wait

chiedi waits for the answer on /dev/tty with poll, one second at a time, then reads it with read. At every second without an answer it checks the mailbox: if the confirmation has appeared, the user confirmed elsewhere; if the message has disappeared, it was revoked; if it has expired, the question stops.

  • The terminal stays in canonical mode: whatever the user is typing stays in the terminal's buffer and is not lost from one second to the next.
  • The question closes within about a second: confirmation from another session (scenario C4b, 0.95 s), revocation (scenario E3, 1.0 s), expiry (tests/engine.sh, group 4).
  • Without /dev/tty (no controlling terminal) the answer counts as “no”: the message stays and comes back later.
  • Only the first character of the answer is checked: s, S, y and Y mean yes in every language.
Chapter 12

Receiving on the desktop

12.1 · The agent's loop

The agent, ams-user agent, starts with the desktop's autostart (/etc/xdg/autostart/ams-agent.desktop) or from systemd-run when ams send does not find one, and lives as long as the graphical session.

  • Only one agent per user: flock(LOCK_EX | LOCK_NB) on $XDG_RUNTIME_DIR/ams-agent.lock; if the lock is taken the agent exits at once, without an error. The descriptor is opened with O_CLOEXEC and is not passed on to zenity: otherwise, if the agent died, one of its orphaned dialogs would hold the lock and the agent started in its place would exit at once (a defect found by the test VM).
  • Ready: after taking the lock the agent writes its PID to $XDG_RUNTIME_DIR/ams-agent.pronto and deletes it on exit (atexit). ams send wakes only that PID (chapter 8.5).
  • Lives as long as the session: the loop goes on as long as sessione_grafica(getuid()) finds an X11 or Wayland session of the user, or until a termination signal arrives.
  • Configuration always current: conf_leggi at every round; a change to AMS_REMIND_MINUTES or AMS_AGENT_POLL applies from the next round.
  • One dialog at a time: the messages not postponed on the desktop channel (state/ID.gui), oldest first (scenario I7).

12.2 · Signals and waits without losses

The agent must react to three things: a new message (SIGUSR1 from ams send), the end of the session (SIGTERM from logind) and the closing of the dialog (SIGCHLD). It handles them without losing signals and without interrupting a confirmation halfway.

  • The five signals stay blocked with sigprocmask all the time, except during the waits, done with ppoll, which unblocks and re-blocks them atomically: a signal that arrives while the agent is working stays pending and interrupts the next wait.
  • Each wait lasts at most one second; the one between two rounds lasts AMS_AGENT_POLL seconds (60) in total, and ends earlier if a wake-up or termination arrives. The periodic check stays as a safety net: a lost signal delays the dialog, it does not lose it.
  • The wake-up clears its flag at the start of the round: a wake-up that arrives while a dialog is open makes the next round start at once.

12.3 · The confirmation dialog

mostra_finestra starts zenity --question --no-markup --width=460 with title, text and buttons in the session's language, and waits for it to finish, checking the mailbox every second as well.

  • --no-markup: the message text is not interpreted as zenity markup. The text has already been cleaned at send time (chapter 8.7).
  • The child that becomes zenity restores the signal mask and handlers before exec: zenity does not inherit the agent's blocked signals.
  • The end of zenity interrupts the wait at once (SIGCHLD): the answer is recorded within a few milliseconds, so an ams remind arriving right after a «Più tardi» finds the postponement already written and removes it (scenario I11; with a check once a second, the VM had found the reminder lost).
  • The wake-up signal does not close the dialog: the agent keeps waiting for it. In the bash prototype the signal interrupted wait and the agent took the dialog as closed, recording a postponement never chosen (test VM, scenario I7).
  • When the session ends the agent waits for the dialog at most 2 seconds, then closes it: a confirmation already given is not lost (scenario I10: «Ho letto» and logout after 0.1 s, confirmation recorded).
  • Timings of the last run recorded in the VM: dialog after sending 0.58 s (I1), closing after a confirmation from the terminal 0.65 s (I5), after a revocation 0.67 s (I6), at graphical login 2.64 s after the login manager restart (I9).

12.4 · The error notification

The agent uses notify-send, if it is installed, for one case only: telling the user that their confirmation has not been recorded (disk full, permissions). The text is fixed: no message content goes through notifications, which may disappear by themselves or be ignored.

i
Note. for the confirmation AMS uses a dialog and not a notification: a GNOME notification may disappear by itself or be ignored, whereas the zenity dialog stays open until the user chooses.
Chapter 13

Confirmations

13.1 · The first one counts

conferma(ID, CANALE) in src/ams-user.c is the only place where a confirmation is born. It writes it to a temporary file, flushes it to disk and publishes it with link, which fails if acks/ID already exists: the confirmation is born whole or not at all, and “already confirmed” stays distinct from “write failed”.

src/ams-user.c (in short)
static int conferma(long long id, const char *canale)
{
	if (esiste(ack)) { segna_letto(id); return 0; }        /* vale la prima */
	if (!c_e("inbox", id, "")) return 3;                  /* ritirato: niente conferma */
	if (scaduto(id)) { segna_letto(id); return 2; }
	fd = open(tmp, O_WRONLY | O_CREAT | O_EXCL | O_CLOEXEC | O_NOFOLLOW, 0644);
	if (fd < 0 || scrivi_tutto(fd, riga, n) < 0 || fsync(fd) < 0 || close(fd) < 0 ||
	    link(tmp, ack) < 0) {                               /* link fallisce se acks/ID esiste */
		unlink(tmp);
		if (esiste(ack)) { segna_letto(id); return 0; }   /* un'altra conferma è arrivata prima */
		evento("CONFERMA_FALLITA", id, U, canale, strerror(errno), "");
		return 1;                                          /* il messaggio resta nella casella */
	}
	unlink(tmp);
	sync_path(acks);                                       /* su disco prima di «Confermato» */
	segna_letto(id);
	evento("CONFERMATO", id, U, canale, "", "");
	return 0;
}
  • The line is data canale: seconds since the Unix epoch, a space, the channel with no translation (desktop, terminale pts/3, terminale tty3).
  • The temporary file acks/.ID.PID starts with a dot: it is never mistaken for a confirmation. If an interruption leaves it behind, it is ignored.
  • If the revocation arrives between the check of inbox/ID and link, the confirmation is born, but ams status does not count it: its date is later than sent/ID/revoked (chapter 10.1).
  • segna_letto renames inbox/ID to read/ID and removes the postponements. If it is interrupted between the confirmation and the move, whoever reads the mailbox next completes the move without asking again (tests/engine.sh, group 1).

13.2 · Two simultaneous confirmations

A user may have the dialog open on the desktop and the question in two terminals. The confirmation must be one: the first to arrive.

  • Two almost simultaneous confirmations produce a single record: link succeeds only once; the other finds acks/ID and only moves the message.
  • The questions and dialogs still open notice it at their next check (within a second) and close: “Message already confirmed elsewhere (for example on the desktop).” in the terminal, while the dialog closes by itself (scenarios C4b and I5).
  • This rule came from a live test of the prototype: the user had to confirm twice, from the dialog and from the terminal.

13.3 · The confirmations read by root

ams status reads the confirmations from the mailbox, which the user controls. That is why it treats them as untrusted data, and their meaning is deliberately limited.

i
Note. “Confirmed” means: the mailbox holds a valid declaration of reading by the user. It is not an action observed by AMS nor a proof of reading: the user controls their own mailbox and could write it themselves, just as they could press «Ho letto» without reading. Whoever uses ams status for an audit must read it this way (chapter 20.1).
Chapter 14

The TUI for administrators

14.1 · Architecture: same data, same commands

ams without arguments, with stdin and stdout on a terminal of at least 80 × 20, opens the TUI of src/tui.c after recovery; in a pipe, or on a smaller terminal, it shows the help. The TUI has no way of its own of doing things and no states of its own: it reads the store with the functions of ams list and ams status, and every action is the command itself.

  • Same functions for reading: the list uses riassumi (the recipients counted in the three states, revoked and expired), the detail uses destinatari (the same line as ams status).
  • The actions are the commands: sending, revoking, reminding and purging run in a child process that calls cmd_send, cmd_revoke, cmd_remind, cmd_purge with stdout and stderr collected on a pipe and shown in a window. An error of the command (die) ends only the child; the child's exit status gives the result. The recipients preview and the history (cmd_log) also come from a child.
  • The decision of the user who wanted the TUI is also a design constraint: while discussing the previews, invented states had appeared (“pending”, “complete”, “incomplete send”, “cancelled”) and were removed; tests/tui.py checks that none of these words appears on the screen.

14.2 · The list

The list shows the messages from the most recent, one per row, with the recipients summary: a three-colour bar and a phrase. It refreshes by itself every 3 seconds.

14.3 · The detail and the history

The detail of a message has two tabs: the recipients, with the status line of ams status coloured according to the state, and the history, that is the output of ams log. It is re-read every 3 seconds and after every action; Esc leaves it.

  • The header shows title, date, sender, expiry (“expires on …” or “expired on …”) and revocation (“revoked on …”, in red); then at most six lines of the text, indented.
  • The tab row repeats bar and phrase: the summary stays visible while scrolling through the list.
  • Colours of the STATO (STATE) column: green confirmed, yellow delivered, red sent. They are the three states, and only those.
  • Keys: Tab switches tab, ↑ ↓ scroll, s and r remind and revoke with the same rules as the list.

14.4 · Writing and sending

The new-message form has four fields: recipients, title, expiry and text. When the recipients field is left, a child performs the same resolution as ams send and shows the number of recipients, or the error in red.

  • One-line fields accept at most 1000 bytes; the text shows the count “85 of 65536 bytes”. The real checks are those of ams send: an error arrives in the result window, “Message not sent”.
  • Editor: Ctrl+E writes the text to a temporary file in /tmp (mkstemp), hands it over to the administrator in SUDO_USER and opens VISUAL, EDITOR, nano or vi with their identity, not as root; then it re-reads the file (at most twice the maximum length, without following links) and deletes it.
  • After sending, the list reloads and the new message appears at the top (tests/tui.py).
i
Note. a defect found while writing tests/tui.py: the child that performs the send also inherited the end of the pipe through which the parent writes the text, and never saw the end of the text. Now it closes it before calling cmd_send.

14.5 · The actions with confirmation

Revoking, reminding and purging always ask for a confirmation that describes the action with the real numbers; the result of the command then appears in a window.

Windows and confirmations are drawn on a copy of the base screen: a later window does not stay on top of the previous one. s confirms, n or Esc cancels.

Chapter 16

Languages

16.1 · Everyone in their own language

Everyone reads AMS in their own language: the administrator the commands, each user the question, the dialog and the buttons. The text of the messages is never translated. Today AMS has Italian and English; English is the language of the texts in the code and the fallback language.

  • What is saved stays language-neutral: the channel of a confirmation is terminale pts/N or desktop and is translated only when shown (canale_testo); events are rewritten from their fields. An administrator using English reads «confirmed on 30/09 17:10 (terminal pts/19)» for the same confirmation that one using Italian reads as «confermato il … (terminale pts/19)» (scenario L3).
  • The question accepts s, S, y and Y in every language (scenario L2).

16.2 · Choosing the language

lingua_scegli in src/lingua.c follows the gettext rules, with one restriction: only codes of 2 or 3 lowercase letters are accepted.

  • What counts is the first one set among LC_ALL, LC_MESSAGES and LANG. If it is C or POSIX (including C.UTF-8), or empty, English applies and LANGUAGE does not count.
  • Otherwise the LANGUAGE list (colon-separated) is tried first, then the language of the chosen value: the part before _, ., @. The first language that has an installed catalog wins (English is always available); if none does, English.
  • A value that is not a code of 2 or 3 lowercase letters (../../tmp/x, a/b) never leads to reading a file: the catalog path is built only from a valid code.
  • Nine cases are tested in tests/prove-unita.c and again in tests/engine.sh (group 8): Italian, English, a language without a translation, C, precedence of LC_ALL and of LC_MESSAGES, a LANGUAGE list, LANGUAGE with C, odd values.

16.3 · The .mo catalog reader

The catalogs are in the gettext format (.mo), but they are read by src/lingua.c, not by libintl. This decision was made after a test: with libintl, a language not installed on the system stays untranslated even when LANGUAGE is forced (with C.UTF-8 the library ignores LANGUAGE), and root must be able to write to every terminal in the language of its user, which differs from its own.

i
Note. the catalogs are root's files, but the reader treats them as arbitrary data: fuzzing also tries arbitrary catalogs (chapter 21.7).

16.4 · Texts, contexts and catalogs

  • In the code, the texts for AMS users are in English inside T("…") (or TC(contesto, "…"), tl(lingua, "…") for a given language; N_(…) for texts translated later). Names, comments and developer notes are in Italian.
  • make pot extracts them into po/ams.pot with xgettext (with the TRADUTTORI comments) and updates the .po files with msgmerge; make compiles them with msgfmt --check, which also checks that every translation has the same %s.
  • tools/check-docs.py fails if a catalog does not pass msgfmt --check, has translations to review, or does not contain all the texts of the code.
  • For a new language a po/XX.po is enough (created, for example, with msginit): the Makefile and install.sh pick it up by themselves.
!
Warning. if the user changes LANG inside the shell (for example in .bashrc), the header written at sending time follows the environment the shell started with; question and answers follow the new one (chapter 23).

Chapter 18

The event log

18.1 · Structured events in the journal

Every relevant fact in the life of a message becomes a structured event in the system journal. The log answers a different question from ams status: not “where does it stand” but “what happened, when, and by whose hand”.

  • evento(EVENTO, ID, UTENTE, CANALE, DETTAGLI, AUTORE) in src/evento.c writes with sd_journal_send a readable text (MESSAGE) and the structured fields. If the journal does not respond, it writes at least the text with syslog.
  • The readable text is in the system language (/etc/default/locale or /etc/locale.conf), the same for everyone; ams log rewrites it from the fields in the reader's language (scenario L4).
  • The details fit on a single line: line breaks become spaces.
  • The log is the history, not the state: states are always derived from the message store, never from the journal (chapter 20.1). Retention of the events follows the journal's rules, not those of AMS: ams purge does not touch them.

18.2 · The fields of an event

For an audit, journalctl AMS_MESSAGGIO=12 -o verbose shows all the fields, _UID included; journalctl -t ams shows the text of all AMS events.

18.3 · The events

18.4 · ams log and trustworthiness

ams log ID reconstructs the history of a message from the events, in the language of whoever runs it; the History tab of the TUI shows the same output.

  • Events are searched with two conditions together: SYSLOG_IDENTIFIER=ams and AMS_MESSAGGIO=ID, and only from the sending date of the message (minus one second): a message store that has been reset reuses the numbers, the journal does not.
  • Anyone can write an event with the AMS_* fields to the journal: _UID says who wrote it, not that it is true. ams log expects root (in test mode, whoever runs it) for the administrator's events and the recipient themselves for RINVIATO, CONFERMATO and CONFERMA_FALLITA; if _UID differs, the line begins with «[non attendibile: scritto da UID N]» (“[not trustworthy: written by UID N]” in English) (scenario J3).
  • An event with an unknown name is shown with its MESSAGE; every line goes through pulisci before it reaches the terminal.

Chapter 19

Error taxonomy

19.1 · Three families of errors

AMS distinguishes three families of errors. Those that can be detected before writing stop the command without leaving traces; those that happen during the work do not stop the other recipients and leave a mark; interruptions leave a state that the next command knows how to repair.

  • Error messages are translated like any other text, except «memoria esaurita» (out of memory) and «formato non valido» (invalid format), which are written in Italian in the code.
  • ams-user does not use die in normal work: it runs inside the prompt or in the graphical session, and every problem it meets becomes “do nothing” or a notice to the user (chapter 11.3).
  • In the TUI a die of the command closes only the child process: its message appears in the result dialog (chapter 14.1).

Chapter 20

Specification

20.1 · Authoritative sources

This chapter is the contract of AMS: what any implementation must respect, regardless of how it is written. The rest of the manual describes how the C version implements it; the bash prototype (0.1.0) worked on the same message store, and the same tests apply to both. Every change to the code respects this chapter or updates it explicitly.

  • A confirmation is a fact declared by the user in their own mailbox; it is valid only if it does not contradict root's message store: its date must not be later than the expiry written in sent/ID/msg nor than the revocation (sent/ID/revoked).
  • “Confirmed” means: the mailbox contains a valid read statement from the user. It is not an action observed by AMS, nor proof of reading: the user controls their own mailbox and could write it themselves. Anyone using ams status for an audit must read it this way.
  • If the user deletes their own copy, the message simply shows as not confirmed; if they alter it (text, expiry), only what they see changes.

20.2 · States and transitions

Each recipient of a message is in one of three states; the state is derived from the files, according to fixed rules (chapter 10.1). There are only these three states (the owner's decision): revocation and expiry are properties of the message, not states; incomplete, failed, ritiro and .cancella-ID are internal marks with which recovery completes or cancels an interrupted operation, and they are not shown as states. An interrupted sending shows for itself: some recipients stay sent.

20.3 · How a message is summarised

In the message list (TUI and ams list) a message is summarised by its recipients: how many are in each of the three states, in words and with a bar (confirmed, delivered, sent), plus the properties revoked and expired. No other word describes the state of a message.

  • The phrase leaves out zero counts; if everyone has confirmed it says «tutti confermato (N)» (“all confirmed (N)” in English).
  • Words such as “pending”, “complete”, “incomplete sending”, “cancelled” (in Italian «in attesa», «completo», «invio incompleto», «annullato») are not states and do not appear: tests/engine.sh (group 3) and tests/tui.py check this.
  • A sending cancelled before it was saved has no recipients to count: ams list reports it with a warning line, the TUI does not show it (chapter 10.4).

Chapter 22

Defects found and reviews

22.1 · The two external reviews

The project went through two external critical reviews, carried out by language models on the technical manual, without the code. Every finding was verified on the code or with a test before being accepted; the point-by-point detail is in docs/revisione-avversariale.md.

  • Criticisms not accepted, with the reason: “the confirmation does not prove reading” (intended: never block, chapter 20.1); “if the terminal is blocked the message does not arrive” (inaccurate: the mailbox acts as a queue); “rewrite in a compiled language right away” (the specification first; the rewrite came later); ams always as root (the user's decision); a pipe in place of acks/ID blocking ams status and an end-of-line comment in ams.conf (inaccurate, tested); a /var/lib/ams prepared before installation (outside the model).
  • A criticism rejected by mistake and then accepted: locks left stuck. The kernel releases the lock when the process dies, but the test VM showed that the agent's lock was inherited by its children.

22.2 · The defects found and fixed

The live tests of the prototype also gave rise to three rules: the first confirmation counts for all channels (one had to confirm twice), waking the agent with a signal (the dialog arrived after 3-4 seconds) and the command in /usr/local/bin instead of sbin (on Debian sbin is not in the PATH of non-root users).

22.3 · From bash to C

Version 0.2.0 is a complete rewrite in C of the bash prototype, decided by the user after the second review: the defects found almost all stemmed from bash (races between check and use, time limits, one process per operation). A language that avoids memory errors by construction had been proposed; the user chose C, with mandatory defences.

i
Note. the bash prototype was removed when the C version passed all the tests; it remains in the repository history. The shell hooks remain scripts, and the dialog remains zenity.

the message in sent/ID/msg, accessible only to root: the only expiry that counts.
recipient (it. destinatario)
a user the message is addressed to; the list is in sent/ID/recipients.
event (it. evento)
a structured line in the journal, with the AMS_* fields (chapter 18).
administrators' group (it. gruppo degli amministratori)
the existing group sudo, wheel or admin: AMS has no group of its own.
fingerprint (it. impronta)
the abbreviated SHA-256 of the code (tools/impronta.sh), recorded with the test results (chapter 21.1).
sent (it. inviato)
state of a recipient who does not yet have the copy in the mailbox.
lock
the file sent/ID/lock used with flock: held by ams send for the whole delivery, it tells a sending in progress from an interrupted one.

25.2 · Terms M–Z (Italian names)

message (it. messaggio)
a text with an optional title and expiry and a sequential number (ID).
test mode (it. modalità di prova)
AMS_TEST=1 with a test message store: the code is tested without root (chapter 4.3).
message properties (it. proprietà del messaggio)
revoked and expired: they apply to the message, not to a recipient, and they are not states.
ready (it. pronto)
an agent that has set up the reception of the wake-up signal and has written its PID to ams-agent.pronto.
linearisation point (it. punto di linearizzazione)
the instant at which an operation is considered to have happened for any observer (chapter 20.4).
recovery (it. recupero)
recupera: completes interrupted sendings, revocations and deletions at the start of the following commands (chapter 8.6).
summary (it. riassunto)
a message described by the counts of its recipients in the three states, in words and with a bar (chapter 10.3).
postponement (it. rinvio)
the answer “no” or «Più tardi» (“Later”): the file state/ID.term or state/ID.gui, whose modification time counts for AMS_REMIND_MINUTES minutes.
revoked (it. ritirato)
property of a message with sent/ID/revoked: it is no longer shown, and later confirmations are not valid.
expired (it. scaduto)
property of a message whose expiry has passed: it is no longer shown, and later confirmations are not valid.
internal marker (it. segno interno)
incomplete, ritiro, failed, .cancella-ID: files through which recovery knows what to complete or cancel. They are not states.
reminder (it. sollecito)
ams remind: removes the postponements of the delivered recipients and wakes up their agent (chapter 9.2).
wake-up (it. sveglia)
the SIGUSR1 signal that ams send and ams remind send to the ready agent.
TUI
the full-screen interface for administrators: ams without arguments in a terminal (chapter 14).
zenity
the program that draws the «Ho letto» / «Più tardi» (“I have read it” / “Later”) dialog on the desktop.
