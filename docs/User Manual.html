    Chapter 1

    Welcome

    1.1 · What RootSpeak is

    RootSpeak — Advanced Messaging System for Linux lets whoever administers a Linux machine send a message to the users and know, for each of them, whether they have confirmed reading it. It is meant for the notices that matter: maintenance, a reboot, a new rule, an account about to expire.

    The administrator writes the message in the full-screen interface of rspeak or with a command. RootSpeak delivers it wherever the user is: in terminal windows (including ssh connections), on the desktop, or at the next login if the user is not logged in at that moment. The user confirms with a click or a single letter, and the administrator sees who has confirmed, when and from where.

    For administrators, RootSpeak offers a single place in which to:

    • write a message and send it to one user, to a group, to everyone or only to whoever is logged in;
    • see how far each recipient has got: sent, delivered or confirmed;
    • remind whoever has not confirmed yet, revoke a mistaken message, give it an expiry;
    • find the history of every message in the system log;
    • delete old messages when they are no longer needed.
    i
    What a confirmation says. a confirmation is a statement by the user (“I have read it”), recorded with date, time and channel. RootSpeak cannot know whether the message was really read, and neither can any other messaging system.

    1.2 · What it does, and what it does not

    RootSpeak, on the other hand, does not do these things, by design:

    • It never blocks anyone. No locked screen, no denied login, no disconnection: the user can always postpone and carry on working. The message comes back later.
    • It is not a chat. Users receive and confirm; they do not reply, do not write to others and have no commands to learn.
    • It does not use the network. It reaches the users of this machine, including those connected remotely with ssh, but not other machines.
    • It does not disturb automated programs. Backups, cron, copies with scp or rsync never see the RootSpeak question: it appears only in interactive shells.

    1.3 · Who this manual is for

    Anyone using RootSpeak for the first time can follow the guided path in chapter 4, which leads from installation to the first confirmation in a few steps. The users who receive the messages do not need to read anything: the dialog and the question explain themselves, and there is no command for them.

    +
    Further reading. the inner workings (message store, delivery, security) are described in the Technical Manual, installed next to this one in /usr/local/share/doc/rootspeak/.

    1.4 · Conventions

    In the examples admin is an administrator; mario, anna and luca are users of the machine server, and @developers is a group. In the dark boxes, lines starting with the prompt (admin@server:~$) are commands to type; orange lines are what RootSpeak shows to the users; red lines are errors. The TUI screenshots are real, taken from RootSpeak while running.

    i
    Version. this manual describes RootSpeak 0.2.0. The command rspeak version shows the installed version.
    !
    Always with sudo. rspeak always works as administrator (root) and asks for the sudo password, even just to show the help: this is a deliberate choice, not a bug.
    Chapter 2

    Installation and first start

    2.1 · Requirements

    RootSpeak runs on a Linux distribution with systemd. It has been tested on Debian 13 with GNOME on Wayland: live, and with automated tests in a test machine and in a virtual machine with a desktop. With X11, other desktops and other systemd distributions it should work the same way, but this has not been tested; without systemd it does not work.

    Installing the packages on Debian and Ubuntu
    admin@server:~$ sudo apt install zenity libnotify-bin gcc make pkg-config libsystemd-dev
    i
    Servers without a desktop. on machines without a desktop zenity is not needed: RootSpeak uses only the terminals. The installation reports “Warning: zenity is missing” but carries on.

    2.2 · Compiling and installing

    1. Open a terminal in the RootSpeak folder and compile, as a normal user:
      admin@server:~/ROOTSPEAK$ make
    2. Run the installation: the script restarts itself with sudo and asks for your password. At the end it confirms “RootSpeak installed”, gives the paths of the command (usable by the sudo group) and of the manuals, and reminds you that sessions already open get the messages in the terminal at once, and the confirmation question from the next shell or the next login.
      admin@server:~/ROOTSPEAK$ ./install.sh
[sudo] password for admin:
RootSpeak installed. Command: /usr/local/bin/rspeak (usable by the sudo group).
Manuals: /usr/local/share/doc/rootspeak/User Manual.html and Technical Manual.html
Sessions already open get messages in the terminal at once, and the
confirmation question from the next shell or the next login.
    3. Check that the command answers:
      admin@server:~$ rspeak version
RootSpeak - Advanced Messaging System for Linux 0.2.0
    +
    Automatic compilation. if make has not been run, or if the programs were compiled for other folders, install.sh compiles on its own. If compilation fails it writes “Build failed: gcc, make, pkg-config and libsystemd-dev are needed”.
    i
    Users already logged in. users who are already logged in receive messages straight away, on the desktop too. The confirmation question in the terminal, instead, arrives from the next terminal window they open: the ones already open have not loaded RootSpeak yet.

    2.3 · What gets installed

    The installation puts everything in the usual Linux places. Besides these files it adds a line, marked # RootSpeak hook, at the end of /etc/bash.bashrc and, if zsh is installed, to the system zshrc: this is what makes the question appear in the desktop's terminals.

    2.4 · The administrators

    The rspeak command belongs to root and to the administrators group the machine already has: sudo on Debian and Ubuntu, wheel on Fedora and similar (failing that, admin or root). RootSpeak has no list of administrators of its own.

    The command and its permissions: root and the sudo group, nobody else
    admin@server:~$ stat -c '%U:%G %a %n' /usr/local/bin/rspeak
root:sudo 750 /usr/local/bin/rspeak
    !
    A single group. joining the sudo group means being able to become root on the whole machine, not only to use RootSpeak. This is intended: sending messages to all users is an administrator's task.

    2.5 · First start

    Right after installation it is worth doing three checks, none of which disturbs anyone.

    1. Open the built-in help: rspeak --help (chapter 9). Leave it with q.
    2. Check the list of messages: it is empty, because nothing has been sent yet.
      admin@server:~$ rspeak list
No messages sent.
    3. Open the TUI by typing rspeak on its own: it shows “No messages sent.” and the keys at the bottom. Leave it with q.
    4. For a complete test, send a message to yourself, as in chapter 4.
    +
    Try it on yourself. a message sent to yourself shows in a few seconds everything the users will see: the text in the terminal, the question at the prompt, the dialog on the desktop.

    2.6 · Upgrading and removing

    Removal: messages and settings stay
    admin@server:~/ROOTSPEAK$ ./install.sh --uninstall
RootSpeak removed. Messages (/var/lib/rootspeak) and configuration (/etc/rootspeak) kept.
    !
    Before --purge. --purge also deletes the record of who confirmed what. If it needs to be kept, copy /var/lib/rootspeak elsewhere first. The events remain in the system log in any case.
    Chapter 3

    RootSpeak at a glance

    3.1 · Two ways of working

    RootSpeak can be used in two ways, which do exactly the same things. Typed on its own in a terminal, rspeak opens the TUI, a full-screen interface inside the terminal: the list of messages, the state of every recipient, the keys to act. Followed by a command (rspeak send, rspeak status…) it does one single thing and returns to the prompt.

    i
    Same commands. every TUI action runs the corresponding command and shows its answer: what you learn in one way also applies to the other.

    3.2 · How the TUI is laid out

    The main screen of the TUI is the list of sent messages. All RootSpeak screens have the same frame: the title at the top left, the time of the last update at the top right, the content in the middle and, at the bottom, the line of keys that can be pressed at that moment.

    • The messages are sorted newest first. [revoked] and [expired] before the text mark those that are no longer shown to the users.
    • In a terminal narrower than 110 columns the phrase gives way to just the count of confirmations out of the total, for example 4/8; the bar stays.
    • If the terminal becomes smaller than 80 columns or 20 lines while the TUI is open, the TUI closes and the terminal returns to how it was.
    • With the NO_COLOR variable the TUI has no colours (chapter 10.3).

    3.3 · The three states of a recipient

    There is only one concept you need to know to use RootSpeak: every recipient of every message is in one of three states. There are no others.

    revoked and expired, on the other hand, are properties of the message: from that moment on the message is no longer shown or shown again to anyone, and whoever had not confirmed stays delivered, with the indication “not confirmed (revoked)” or “not confirmed (expired)”.

    The list summarises each message with its recipients in the three states, in two forms: the bar of 12 coloured marks and the phrase, for example “4 confirmed · 3 delivered · 1 sent”. When everyone has confirmed, the phrase becomes “all confirmed (8)” and the bar is entirely green.

    +
    What about those who postpone? whoever has postponed is not in a separate state: they stay delivered. The message details say when they last postponed (chapter 6.2).

    3.4 · Map of commands and keys

    In the TUI the ? key opens the list of keys over the message list; any key closes it. The complete list of commands is in rspeak --help.

    Chapter 4

    First steps

    4.1 · The path

    This path leads from a freshly installed RootSpeak to the first confirmation, in four stages. The recipient of the first message can be the administrator themselves: that way you see with your own eyes what the users receive. Each stage refers to the chapter that explains it in detail.

    4.2 · Sending the first message

    The simplest way is the TUI. Here the message goes to Mario; to try it on yourself, just type your own name.

    1. Open a terminal and type rspeak. When prompted, enter your password: rspeak always asks for it, because it works as administrator.
      admin@server:~$ rspeak
[sudo] password for admin:
    2. In the list of messages press n: the New message screen opens.
    3. In the To field type mario and press Tab: on the right 1 recipient appears.
    4. In the Title field type Maintenance; leave Expires empty and move to Text with Tab.
    5. Type the text: On Saturday from 8 am to 12 noon the server will be off. Start a new line with Enter.
    6. Press Ctrl+S. The summary Send the message? appears: press y to confirm.
    7. The Message sent window reports the answer of RootSpeak, for example “Message 1 sent to 1 user.” Any key takes you back to the list, where the message is at the top.

    The same message, with a single command (same text, same reply):

    admin@server:~$ rspeak send --to mario --title Maintenance "On Saturday from 8 am to 12 noon the server will be off."
Message 1 sent to 1 user.
    +
    The number. the message number (here 1) is needed for the commands status, log, revoke and remind. In the TUI it is not needed: you pick the message from the list.

    4.3 · What the user sees

    If Mario is logged in, the message reaches him at once, in all his sessions. On the desktop this dialog appears, above the other windows:

    In terminal windows the text appears at once, under the heading “RootSpeak · Message from the administrator”; at the next prompt RootSpeak asks for the confirmation, and after the answer y replies “[RootSpeak] Confirmed.”:

    In Mario's terminal
    ── RootSpeak · Message from the administrator · Maintenance · 01/10 10:49 ──
On Saturday from 8 am to 12 noon the server will be off.
────────────────────────────────────────
[RootSpeak] Do you confirm you have read the message? [y/N] y
[RootSpeak] Confirmed.
mario@server:~$
    i
    One confirmation is enough. confirming once, anywhere, is enough: the dialog closes by itself if Mario answers in the terminal, and vice versa. If Mario is not logged in, he will find the message at his next login. chapter 8 describes everything the users see.

    4.4 · Seeing who has read it

    In the list the message shows its recipients in the three states: before Mario logs in “1 delivered”, after his confirmation “all confirmed (1)”. With Enter you open the message and see the state of every recipient, with date, time and channel of the confirmation.

    The same, with a command
    admin@server:~$ rspeak status 1
Message 1 · Maintenance · 01/10 10:49 · from admin
  │ On Saturday from 8 am to 12 noon the server will be off.

USER             STATE
mario            confirmed on 01/10 10:50 (desktop)
    +
    And then? the TUI updates itself every 3 seconds: keeping it open on the message, you see the confirmations arrive one after another.
    Chapter 5

    Writing and sending messages

    5.1 · Choosing the recipients

    The To field of the TUI and the --to option of the commands say who receives the message. Several recipients can be given, separated by commas and without spaces: anyone who appears more than once, for example because they belong to two groups, receives the message only once.

    i
    Good to know. a group given with @ includes all its members, even the accounts that all leaves out. In the TUI, when you move from the To field to the next one, the number of recipients appears on the right, or an error if a name does not exist: this is checked before sending.
    !
    online is a snapshot. online is evaluated at the moment of sending: someone who logs in a minute later does not receive the message. For a notice that must reach everyone sooner or later, use all.

    5.2 · Title and text

    The title is optional and fits on one line: it appears at the top of the message in the terminal, in the desktop dialog and in the TUI list. The text can have several lines.

    notice.txt, sent below to everyone with a title
    From Monday 19 October passwords expire every 90 days.
At the first login after the expiry the system will ask you to change it.
For problems: IT office, extension 214.
    admin@server:~$ rspeak send --to all --title "New rule for passwords" --file notice.txt
Message 3 sent to 24 users.
    i
    Order matters. in commands, the options must be written before the text: everything after the first word that is not an option is part of the message.

    5.3 · The expiry

    Every message asks for confirmation. For notices that are only valid for a short time, such as “the service restarts in 5 minutes”, you add an expiry: once that moment has passed the message is no longer shown or asked again, and whoever has not seen it in time will never see it.

    admin@server:~$ rspeak send --to online --expires 15m "The web service restarts at 13:00."
Message 2 sent to 3 users.
    • On expiry, a dialog that is still open closes by itself, and a question waiting in the terminal is interrupted with “[RootSpeak] The message has expired.”
    • A confirmation given after the expiry does not count: the recipient stays delivered, “not confirmed (expired)”.
    • In the list the message appears with [expired] in front; the detail view says when it expired.
    i
    Dates. dates in words are read by the system's date command, which understands them in English only ("saturday 12:00", "tomorrow 18:00"). The year-month-day hours:minutes format always works. A date already in the past is refused with “the expiry is already in the past”.

    5.4 · Writing in the TUI

    In the TUI the n key opens the New message screen: three one-line fields and the text box below them.

    Ctrl+S shows a summary with the recipients (and how many there are), title, expiry and length of the text. y sends, n or Esc returns to the message without losing anything.

    • If sending succeeds, Message sent appears with the reply from RootSpeak; any key returns to the list.
    • If something goes wrong, Sending result appears with the reason: a wrong recipient (for example “rspeak: no such user: mrio”) stops the sending, and any key returns to the message so it can be corrected; a copy that could not be written is listed, and RootSpeak retries by itself at the next command.

    5.5 · Your own editor

    For long texts your own editor is more convenient. Ctrl+E closes the TUI for a moment and opens the text written so far in the editor; when you save and quit you return to the TUI with the updated text.

    1. In the new message, press Ctrl+E.
    2. Write or paste the text in the editor, save and quit (with nano: Ctrl+O, Enter, Ctrl+X).
    3. Check the text in the box and send with Ctrl+S.
    i
    Security. the editor runs with the administrator's identity, not as root: it opens a temporary file that belongs to the administrator and that RootSpeak deletes on return.

    5.6 · What happens when sending

    When a message is sent, RootSpeak saves it, puts a copy in each recipient's mailbox and makes it appear at once wherever the user is logged in. It all happens in a few moments.

    The text written to the terminals when the message is sent appears even if the user is working; the confirmation question, instead, only arrives when the user is back at the prompt, so as not to interrupt a command halfway.

    5.7 · Ready-made commands

    +
    Automatic sending. in cron (root's crontab, sudo crontab -e) rspeak is already root and does not ask for the password. It is best to give the full path of the command.
    Chapter 6

    Following the confirmations

    6.1 · The list of messages

    The main screen of the TUI (chapter 3.2) and the rspeak list command show all the messages sent, each summarised by its recipients in the three states. The TUI puts the most recent first and updates by itself; rspeak list lists them from the oldest, once.

    The same four messages as in the screenshot in chapter 3
    admin@server:~$ rspeak list
ID    DATE         TEXT                                      RECIPIENTS
1     01/10 10:49  Tonight at 11 pm the mail server is upda  all confirmed (3)
2     01/10 10:49  On Saturday from 8 am to 12 noon the ser  4 confirmed · 3 delivered · 1 sent
3     01/10 10:49  Your account expires on Friday: please d  1 delivered
4     01/10 10:49  [revoked] Reboot at 1 pm.                 2 delivered
    i
    Recipients. the phrase counts recipients, not the people who have seen the message: “3 delivered” means three people with the copy in their mailbox who have not confirmed yet, logged in or not.

    6.2 · The state of each recipient

    Pressing Enter on the list opens the selected message: at the top title, date, sender, expiry and any revocation, then the first lines of the text, then two tabs. The Recipients tab shows the state of each user, with the colours of the bar.

    The same list, for one message at a time, is obtained with rspeak status followed by the number:

    The state of the recipients with a command; each status line is explained in the table below
    admin@server:~$ rspeak status 2
Message 2 · Maintenance · 01/10 10:49 · from root
  │ On Saturday from 8 am to 12 noon the server will be off for disk maintenance.
  │ Please save your work by Friday evening.

USER             STATE
admin            confirmed on 01/10 10:49 (terminal pts/0)
anna             confirmed on 01/10 10:49 (desktop)
dario            sent, not delivered: the copy could not be written (see the log; the next rspeak command will retry)
fabio            confirmed on 01/10 10:49 (desktop)
kora             delivered, postponed on 01/10 10:49
luca             delivered
mario            delivered, postponed on 01/10 10:49
zeno             confirmed on 01/10 10:49 (terminal pts/2)

    Above the list, rspeak status writes REVOKED on … if the message has been revoked and EXPIRED if the expiry has passed. In the TUI the same information is in the line at the top, in red for a revocation.

    +
    Message keys. in the Recipients tab you scroll with ↑ ↓ and PgUp PgDn; m reminds and r revokes this very message; Esc returns to the list.

    6.3 · The life of a message

    Every message has a history made of events: the sending, the delivery to each recipient, the postponements, the reminders, the confirmations, a possible revocation. Events change the state of a recipient at only two points: when the copy arrives in the mailbox and when the user confirms.

    !
    No going back. a confirmation is final: it cannot be undone, neither from the TUI nor from the commands. To ask everyone again, send a new message.

    6.4 · The history of a message

    The message's History tab, opened with Tab, lists the events of the message taken from the system log, oldest first, with date and time to the second.

    With a command, the same history is read with rspeak log:

    The history with a command; each kind of line is explained in the table below
    admin@server:~$ rspeak log 2
Message 2 · Maintenance · 01/10 10:49
2026-10-01 10:49:29  message 2 delivered to admin (terminals written: 0)
2026-10-01 10:49:29  message 2 delivered to anna (terminals written: 0)
2026-10-01 10:49:29  message 2: ERROR, copy for dario not written
2026-10-01 10:49:29  message 2 delivered to mario (terminals written: 0)
2026-10-01 10:49:29  message 2 sent by root to: admin anna dario fabio kora luca mario zeno
2026-10-01 10:49:42  user anna: confirmed reading message 2 (desktop)
2026-10-01 10:50:03  user mario: postponed message 2 (terminal)
2026-10-01 10:56:36  message 2: 3 recipients reminded by admin
    i
    History and state. the history comes from the system log, which the machine may rotate and delete after a while according to its settings. The state of the recipients, on the other hand, comes from the RootSpeak message store and remains until the message is deleted.

    6.5 · The system log

    Every event is also written to the machine's system log, with the tag rspeak. It is the trail to use if someone asks “who sent what, and when”, even for messages that have already been deleted.

    The system log: the same lines as in the history above
    admin@server:~$ sudo journalctl -t rspeak --since today
Oct 01 10:49:29 server rspeak[20914]: message 2 delivered to anna (terminals written: 0)
Oct 01 10:49:29 server rspeak[20914]: message 2 sent by root to: admin anna dario fabio kora luca mario zeno
Oct 01 10:49:42 server rspeak[21310]: user anna: confirmed reading message 2 (desktop)
    • User events (postponements, confirmations) are written by the users themselves: rspeak log checks who wrote them and flags suspicious ones (chapter 11.5).
    • Deleting with rspeak purge removes the message from the message store, but its events remain in the log.

    6.6 · Searching for a message

    When there are many messages, the / key of the TUI shows only those that contain a given text, searched in the title and in the whole message, ignoring upper and lower case.

    i
    No results. if no message contains the text, the list says “No message contains the search text.” Accented letters must be typed in the same upper or lower case as in the message.
    Chapter 7

    Revoking, reminding, cleaning up

    7.1 · Revoking a message

    A message sent by mistake, or no longer valid, is revoked: in the TUI with r on the selected message (in the list or in the open message), from the command line with rspeak revoke. Before revoking, the TUI always asks for confirmation.

    With a command
    admin@server:~$ rspeak revoke 4
Message 4 revoked.
    !
    Text already written stays. the text that already appeared in the terminals when the message was sent cannot be erased: it is already on the user's screen. Revocation only stops the confirmation requests and the dialogs.
    i
    Revocation during sending. if the message is still being sent to many recipients, the revocation waits a moment and stops the delivery at the next recipient; whoever already has the copy loses it. If some mailbox cannot be reached, RootSpeak says so (“some copies could not be removed from the mailboxes”) and retries by itself.

    7.2 · Reminding those who have not confirmed

    Whoever postponed sees the message again after 30 minutes. If it is needed sooner, send a reminder: in the TUI with m, from the command line with rspeak remind. The question comes back at the next prompt and the dialog reappears at once on the desktop, even if the user had just postponed it.

    With a command
    admin@server:~$ rspeak remind 2
Message 2: 3 recipients reminded.
    • A revoked or expired message cannot be reminded: the command replies “rspeak: message 4 has been revoked: nobody to remind” or “rspeak: message 4 has expired: nobody to remind”.
    • If everyone has already confirmed, nobody is disturbed and the command says so: “Message 2: everyone has already confirmed, nobody to remind.”
    • The reminder is recorded in the message's history and in the log, together with who asked for it.
    • For users who are not logged in, a reminder changes nothing: they will see the message at their next login anyway.
    +
    In moderation. an occasional reminder works better than many: people who get the dialog in front of them every five minutes tend to confirm without reading.

    7.3 · Deleting old messages

    Messages and confirmations stay in the message store until they are deleted. Purging removes the messages sent more than a certain time ago, together with the copies and confirmations in the users' mailboxes.

    1. In the list press p: Delete old messages opens, with 90d already filled in.
    2. Change the duration if needed (90d days, 12h hours, 30m minutes) and press Enter.
    3. Read the summary Delete old messages? and confirm with y.
    4. The next dialog shows the reply from RootSpeak, for example “Deleted 12 messages older than 90d.”
    With a command
    admin@server:~$ rspeak purge 90d
Deleted 12 messages older than 90d.
    • A deleted message disappears from the list and from rspeak status; if someone had not confirmed it yet, they will no longer be asked.
    • A sending still in progress is not touched.
    • The system log keeps the events of the message and that of the deletion (“message 1 deleted by admin (older than 90d)”).
    • Message numbers are not reused: the next message takes the number after the last one.
    !
    Final. deletion cannot be undone. If you need to keep the list of confirmations, first save the output of rspeak status for the messages you care about.

    7.4 · When an action cannot be carried out

    Not every action makes sense on every message. When a key has no effect, the TUI simply does nothing; the commands, instead, reply with an error.

    i
    Always a confirmation. no TUI action starts without a confirmation: the message to revoke, the people to remind and the messages to delete are always shown first. n or Esc cancel.

    All these actions are reserved to administrators and are recorded in the log under their name: for rspeak the author is whoever used sudo, not root (chapter 11.1).

    Chapter 8

    What users see

    8.1 · On the desktop

    On the desktop the message appears by itself, on top of the other windows, a few moments after it is sent. The user does not have to do anything to receive it: at graphical login a small RootSpeak program starts, the desktop agent, which waits for messages. RootSpeak speaks English, whatever the language of the session; the message text arrives exactly as the administrator wrote it.

    • The top of the dialog shows the message title and the date it was sent; if the message has no title, only the date.
    • If there are several messages, the dialogs appear one at a time, from the oldest to the most recent.
    • The dialog closes by itself if the user confirms from a terminal, if the administrator revokes the message or if the message expires.
    i
    Confirmation not recorded. if the confirmation cannot be saved (for example because the disk is full), the desktop shows the notice above and the message is asked again: the confirmation is never lost silently. The notice requires notify-send.

    8.2 · In the terminal

    In every terminal window of the user, whether local, inside the desktop, in tmux or connected through ssh, the text appears the moment the message is sent, even while the user is working:

    When the message is sent: header with title and date, then the text
    mario@server:~/projects$ make
gcc -O2 -c main.c

── RootSpeak · Message from the administrator · Maintenance · 30/09 16:55 ──
On Saturday from 8 am to 12 noon the server will be off.
────────────────────────────────────────
gcc -O2 -o test main.o

    As soon as the user is back at the prompt (if already at the prompt, just press Enter), RootSpeak shows the message again and asks for confirmation:

    At the next prompt: the message again, and the question
    ── RootSpeak · Message from the administrator · Maintenance · 30/09 16:55 ──
On Saturday from 8 am to 12 noon the server will be off.
────────────────────────────────────────
[RootSpeak] Do you confirm you have read the message? [y/N] y
[RootSpeak] Confirmed.
mario@server:~/projects$

    After a postponement, until the next question, only a one-line reminder appears at each prompt:

    If the user postpones: a one-line reminder at each prompt
    [RootSpeak] Do you confirm you have read the message? [y/N] n
[RootSpeak] You will be asked again in 30 minutes.
mario@server:~/projects$ ls
main.c  main.o  test
[RootSpeak] You have 1 message from the administrator to confirm.
mario@server:~/projects$
    i
    Full-screen programs. if the user is running a full-screen program, such as an editor, the text sent to the terminal is drawn over the screen, as happens with wall. Nothing is lost: the screen fixes itself, or with Ctrl+L, and the question only comes when the user leaves the program.

    8.3 · Shells

    The confirmation question in the terminal depends on the user's shell. The text shown when the message is sent, instead, always arrives, whatever the shell.

    • The question only appears in interactive shells: scripts, cron, scp, rsync and commands run with ssh server command never see it.
    • Terminal windows already open when RootSpeak is installed receive the text, but the question only from the next window or the next login.
    • If zsh is installed after RootSpeak, re-running ./install.sh is enough to get the question in zsh; fish, instead, gets it even if installed later.
    !
    Logins with su. with su - mario the terminal window still belongs to whoever opened it: the text sent with the message does not appear, the question at the prompt does. With ssh mario@server everything works normally.

    8.4 · Users who are not logged in

    Users who are not logged in find the message at their next login, however they log in. Meanwhile it is already delivered: the copy is in their mailbox, waiting for them.

    8.5 · Several sessions, one confirmation

    A user with several open sessions, for example the desktop and two ssh connections, receives the message in all of them. Confirming once is enough.

    The dialog closes by itself if the user confirms from a terminal, and the question in the terminal closes if the user confirms on the desktop. The message status keeps the first confirmation, with the channel it came from: desktop or terminal pts/2.

    i
    Separate postponements. postponing, instead, applies to the channel where it is done: a user who presses “Later” on the desktop still sees the question in the terminal, and vice versa.

    8.6 · Postponing and reminders

    RootSpeak never blocks work: the user can always postpone. But whoever postpones is asked again, at regular intervals, until they confirm.

    The 30-minute interval is the same for the dialog and for the terminal and can be changed in the settings (chapter 10). Meanwhile the administrator sees in the message details who postponed and when.

    8.7 · Explaining RootSpeak to users

    Users have no RootSpeak commands and do not need to learn anything. It can still help to answer a few questions: the table collects the most common ones, with short, accurate answers to pass on as they are.

    +
    The first message. for an important notice it is worth telling users, with the first message, what the dialog and the question are: the first message can explain RootSpeak itself.
    Chapter 9

    The built-in help

    9.1 · Opening the built-in help

    Everything needed to use rspeak is also inside the command itself: rspeak --help (or rspeak help or rspeak -h) opens a full-screen guide, divided into five tabs.

    i
    Always with sudo. like every rspeak command, the built-in help also asks for the sudo password. The texts of the Commands and Options tabs are the same as in chapter 13 of this manual.

    9.2 · Moving around the built-in help

    At the bottom right the help shows which lines of the tab are being viewed, for example “lines 1-16/25”. Each tab remembers where you had got to. The help adapts when the window is resized; on exit the terminal goes back exactly as it was.

    +
    For vi users. the keys h j k l are the same as in vi and less: if you know them, you can use them here too.

    9.3 · Small terminals and plain text

    The same guide has three forms, and rspeak picks the right one by itself.

    Searching the built-in help with grep
    admin@server:~$ rspeak --help | grep -A2 -- '--expires DURATION'
       --expires DURATION
              Expiry, after which the message is no longer shown: 30m, 2h, 3d or
              a date and time ("2026-10-04 12:00").
    i
    And rspeak on its own? rspeak on its own, too, in a pipe or in a terminal smaller than 80 columns or 20 lines, shows the built-in help instead of the TUI.
    Chapter 10

    Settings

    10.1 · The settings file

    RootSpeak has two settings, and they live in a single file, /etc/rootspeak/rootspeak.conf. They are fine as installed; change them only for particular needs.

    /etc/rootspeak/rootspeak.conf, as RootSpeak installs it
    # RootSpeak - Advanced Messaging System for Linux: configuration
# A data file, not a script: KEY=value lines with positive whole numbers.
# Unknown keys and invalid values are ignored.

# After how many minutes a message postponed by the user is shown again
RSPEAK_REMIND_MINUTES=30

# Every how many seconds the desktop agent checks the messages again
# (new messages wake it at once anyway)
RSPEAK_AGENT_POLL=60
    i
    Data only. the file contains only data: it is not a script and is never executed. A typing mistake does not stop RootSpeak, it only makes it use the default value.

    10.2 · Changing a setting

    1. Open the file with administrator rights:
      admin@server:~$ sudo nano /etc/rootspeak/rootspeak.conf
    2. Change the value, for example RSPEAK_REMIND_MINUTES=15, save and exit.
    3. There is nothing to restart: the value applies at once to terminals (from the next prompt) and to the desktop from the agent's next check.
    !
    Permissions. the file must remain owned by root and writable only by root, as the installation leaves it: all users read it, to know when to ask the messages again.
    i
    Upgrades. a RootSpeak upgrade does not overwrite /etc/rootspeak/rootspeak.conf; ./install.sh --purge deletes it.

    10.3 · Colours, pager and editor

    A few environment variables change the behaviour of rspeak for the administrator who sets them. Since rspeak always re-runs itself with sudo, they only get through if sudo keeps them.

    To have sudo keep them, add a line to its settings, always with visudo:

    Keeping the variables through sudo
    admin@server:~$ sudo visudo -f /etc/sudoers.d/rootspeak
# in the file:
Defaults env_keep += "NO_COLOR PAGER VISUAL EDITOR"
    !
    For all of sudo. this line applies to every command run with sudo, not just rspeak. Add only the variables you need.
    +
    Editor and security. the editor opened by rspeak runs with the administrator's identity, not as root: keeping EDITOR does not give it extra powers.
    Chapter 11

    Security and privacy

    11.1 · Who can use RootSpeak

    Only the machine's administrators can use rspeak: the members of the sudo group (wheel on Fedora and similar systems). RootSpeak keeps no list of its own: whoever joins or leaves the group gains or loses access from their next login to the machine (chapter 2.4).

    An ordinary user cannot even start the command
    mario@server:~$ rspeak list
bash: /usr/local/bin/rspeak: Permission denied
    • rspeak always works as administrator, even to show the help or the version: if it is not already root, it restarts itself with sudo, which asks for the password.
    • In messages and in the log the author is the administrator who used sudo, not a generic “root”: “message 3 sent by admin to: …”. Whoever runs rspeak directly as root (for example from cron) appears as root.
    • Users have no RootSpeak command at all: they can neither send messages nor see who has confirmed.

    11.2 · Who sees the messages

    Each user sees only the messages sent to them. The message store in /var/lib/rootspeak/ is split into two parts with different permissions.

    i
    Root does not go in as root. RootSpeak always enters a user's mailbox with that user's identity, even when the administrator is in command: this way a user cannot trick root into writing where it should not.

    11.3 · What a confirmation is worth

    The confirmation records that the user states they have read the message, with date, time and channel, like the read receipts of a messaging app. It cannot prove that they really read it.

    i
    A statement. the mailbox belongs to the user: an expert user could record a confirmation without opening the dialog. It is still their own statement, like the click on “I have read it”.
    +
    When more is needed. for notices that require a real commitment (a rule to follow, an authorisation) the RootSpeak confirmation is a reminder, not a signature: a separate document is needed.

    11.4 · Safe text

    Before saving a message, RootSpeak removes from the text and the title the invisible characters and the codes that change the colours, title or behaviour of terminal windows. A message therefore cannot alter users' terminals, even if the text was pasted from an unknown source.

    What RootSpeak reads from the users' mailboxes (confirmations, postponements) is also cleaned before it is shown to the administrator.

    11.5 · How reliable the log is

    The system log is a convenient trail, but anyone on the machine can write lines tagged rspeak into it. That is why rspeak log and the TUI check who really wrote each event and flag the suspicious ones.

    A forged confirmation: Luca (UID 1003) wrote a line in Anna's name; the other lines are ordinary ones, like those in chapter 6.4
    admin@server:~$ rspeak log 3
Message 3 · New password rule · 30/09 19:05
2026-09-30 19:05:12  message 3 delivered to anna (terminals written: 1)
2026-09-30 19:05:12  message 3 sent by admin to: anna luca
2026-09-30 19:06:40  [not trustworthy: written by UID 1003] user anna: confirmed reading message 3 (desktop)
    !
    Trust the state. a line marked “not trustworthy” must be disregarded. The true state of a recipient is the one shown in the message details and by rspeak status, which comes not from the log but from the message store: there confirmed means that the confirmation is in the user's mailbox.
    Chapter 12

    Troubleshooting

    12.1 · Error messages

    When a command fails, rspeak prints a line in red that starts with rspeak:, says what to correct and exits with status 1. In the TUI the same line appears in the result dialog.

    A typical error: a misspelt user name
    admin@server:~$ rspeak send --to mrio "Meeting at 11."
rspeak: no such user: mrio

    12.2 · Frequent problems

    12.3 · “I didn't see any message”

    It is the most common question. The answer is almost always in the message details and in its history.

    1. Open the message in the TUI (Enter) or run rspeak status ID, and find the user's line.
    2. If it is confirmed, the line says when and from where: for example “confirmed on 30/09 16:56 (desktop)”. The user has confirmed, perhaps without reading carefully (chapter 11.3).
    3. If it is delivered, look at the details: “written to 2 terminals” means that the text appeared on their screens; “postponed on …” that they saw the question or the dialog and postponed it. If neither is there, they have probably not logged in yet.
    4. If it is sent, the copy did not reach their mailbox: see chapter 12.4.
    5. In the History tab (Tab), or with rspeak log ID, you find all the events, postponements included, to the second.
    6. If needed, remind them (chapter 7.2): the dialog comes back on their desktop at once.
    +
    Unusual shells. a user who works only through ssh and with a shell such as tcsh does not get the question in the terminal: they see the text when it is sent, but can confirm only from the desktop. With bash, zsh or fish the problem does not arise.

    12.4 · Interrupted sendings

    If a sending is interrupted halfway (the disk fills up, rspeak is stopped, the power goes) RootSpeak does not lose the message: the next time it is used, it resumes from where it stopped.

    i
    When it starts. recovery starts at the beginning of rspeak send, list, status, revoke, remind, log and when the TUI opens. Nothing is needed other than using RootSpeak.
    !
    Full disk. with a full disk the users' confirmations cannot be saved either: users see “The confirmation could not be recorded” and the message is asked again. Freeing space in /var/lib solves both.

    12.5 · Useful files and folders

    +
    Where to look. when something does not add up, the places to look are, in order: the message details, its history, the log with sudo journalctl -t rspeak, and the built-in help.
    Chapter 13

    Command reference

    13.1 · Syntax

    This chapter lists all the commands and options of rspeak. The texts of the commands, options and examples are the same as those of the built-in help (rspeak --help, chapter 9): this page is generated from the same texts, so the two cannot diverge.

    The syntax, from the help in text form
    admin@server:~$ rspeak --help | head -16
RSPEAK(1)                        rspeak manual                         RSPEAK(1)

NAME
       rspeak — sends messages to the users of the machine and tracks their read
       confirmation

SYNOPSIS
       rspeak send --to DEST [options] [TEXT]
       rspeak list
       rspeak status ID
       rspeak
       rspeak revoke ID
       rspeak remind ID
       rspeak log ID
       rspeak purge DURATION
       rspeak version
    i
    Always as root. every command, version and --help included, restarts itself with sudo if it is not already root.

    13.2 · Commands

    The commands of rspeak, with the text of the built-in help.

    (no command)
    In a terminal, opens the interactive interface: the messages with their recipients and history; write and send, revoke, remind, delete old messages. In a pipe, shows this guide.
    send [options] [TEXT]
    Sends a message to the recipients given with --to. Without TEXT or --file, the text is read from stdin.
    list
    Lists the messages sent, with how many recipients have confirmed each one.
    status ID
    Shows the text of the message and the state of each recipient: sent, delivered (in their mailbox) or confirmed, with date, time and channel.
    revoke ID
    Revokes a message: whoever has not seen it yet will not see it, and dialogs and questions still open close by themselves.
    remind ID
    Reminds whoever has not confirmed yet: the question comes back at their next prompt and the dialog reappears on the desktop, even if they had postponed it.
    log ID
    Shows the history of the message from the system log: sending, deliveries, postponements, confirmations and revocation, with date and time.
    purge DURATION
    Deletes the messages sent more than DURATION ago (for example 90d), with the copies and confirmations in the users' mailboxes; the events stay in the system log.
    version
    Shows the RootSpeak version.
    help, --help, -h
    Shows this guide.

    13.3 · Send options

    The options of rspeak send. They must be written before the text of the message; in the TUI they correspond to the fields of the new message (chapter 5.4).

    --to DEST
    Recipients, separated by commas without spaces: a user (mario), a Unix group (@developers), all (every human user) or online (only those logged in now).
    --title TITLE
    Title shown in the message header and in the desktop dialog.
    --expires DURATION
    Expiry, after which the message is no longer shown: 30m, 2h, 3d or a date and time ("2026-10-04 12:00").
    --file FILE
    Reads the message text from FILE.

    13.4 · Examples

    13.5 · Exit status and environment

    The exit status makes it possible to use rspeak in scripts:

    In a script
    admin@server:~$ rspeak send --to online --expires 15m "Reboot at 1 pm." || echo "sending failed"
Message 7 sent to 3 users.
    Chapter 14

    Glossary

    14.1 · Terms

    all
    Special recipient: all the users of the machine with a UID of 1000 or above and a real shell.
    built-in help
    The tabbed help that opens with rspeak --help.
    channel
    Where a confirmation came from: desktop or terminal pts/N or terminal ttyN.
    confirmation
    The user's statement that they have read a message: a click on “I have read it” or the answer “y”. It is final and applies to all their sessions.
    confirmed
    Third state of a recipient: they have stated that they read the message. It is their statement, not proof that they really read it.
    delivered
    Second state: the copy of the message is in the user's mailbox, and the user has not confirmed yet. Whoever postpones stays delivered.
    desktop agent
    The small RootSpeak program that starts at every graphical login and shows the confirmation dialogs. It is not a command: it starts by itself.
    event
    A fact in the history of a message (sending, delivery, postponement, reminder, confirmation, revocation, deletion), written to the system log.
    expiry
    The moment after which a message is no longer shown (--expires). Expired is a property of the message, not a state of the recipients.
    mailbox
    The space where RootSpeak keeps a user's messages, their confirmations and their postponements. Only they (and root) can open it.
    message store
    The folder /var/lib/rootspeak/: the reference copies of the messages and the users' mailboxes.
    online
    Special recipient: among the users of all, those logged in at the moment of sending.
    postpone
    Pressing “Later” or answering anything other than “y”: the message is shown again after 30 minutes. It is not a state.
    purge
    Deleting the messages older than a given duration: rspeak purge or the p key in the TUI.
    recipients
    The users who receive a message: names, @group, all, online.
    recovery
    The automatic completion of a sending left halfway, the next time rspeak is used.
    remind
    Asking again, immediately, for the confirmation from those who are still delivered: rspeak remind or the m key in the TUI.
    revoke
    Withdrawing a message with rspeak revoke or the r key: whoever has not seen it will no longer see it. Revoked is a property of the message, not a state of the recipients.
    sent
    First state: the message has left, but the copy is not yet in the user's mailbox.
    session
    A user's access to the machine: the desktop, a console, an ssh connection.
    system log
    The machine's log (the journal), where RootSpeak writes its events with the tag rspeak.
    TUI
    The full-screen interface, inside the terminal, that opens when you type rspeak on its own.
